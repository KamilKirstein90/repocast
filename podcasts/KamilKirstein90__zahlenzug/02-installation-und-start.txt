In der letzten Folge hast du erfahren, was Zahlenzug ist, ein Zählspiel mit einem wachsenden Zug, und heute bringen wir es auf deinem eigenen Rechner zum Laufen.

Fangen wir mit der einfachsten Variante an, nämlich gar nichts zu installieren. Das Spiel ist über GitHub Pages veröffentlicht, also als ganz normale Webseite erreichbar. Auf einem Android-Handy öffnest du die Seite in Chrome, tippst oben rechts auf das Menü mit den drei Punkten und wählst "Zum Startbildschirm hinzufügen" oder "App installieren". Danach liegt ein Zahlenzug-Symbol auf dem Startbildschirm. Startest du das Spiel von dort, läuft es im Vollbild. Die Projektbeschreibung empfiehlt, das Handy quer zu halten und die Lautstärke aufzudrehen, denn ohne Ton fehlt die halbe Belohnung. Und noch ein netter Tipp für Eltern steht dort: Android hat eine Funktion namens Bildschirmfixierung. Damit kann das Kind die App nicht versehentlich verlassen.

Jetzt aber zur Entwicklerseite. Du brauchst eigentlich nur zwei Dinge: Git und eine aktuelle Node-Installation mit npm. Zuerst klonst du das Repository von GitHub. Dann wechselst du in den Ordner und installierst die Abhängigkeiten mit npm install. Das geht schnell, denn es gibt genau drei Abhängigkeiten, und alle drei sind nur Entwicklungswerkzeuge. Das ist zum einen Vite, der Build- und Entwicklungsserver, zum anderen TypeScript für die Typprüfung, und drittens ein kleines Paket namens gh-pages, das zum Veröffentlichen auf GitHub Pages dient. Zur Laufzeit im Browser hängt das Spiel von keiner einzigen fremden Bibliothek ab.

Zum Entwickeln startest du den Server mit npm run dev. Interessant ist hier ein Detail in der package Datei: Das Dev-Skript ruft Vite mit dem Schalter host auf. Das bedeutet, der Entwicklungsserver lauscht nicht nur auf localhost, sondern auf allen Netzwerkschnittstellen. Vite zeigt dir dann zusätzlich eine Adresse im lokalen Netzwerk an. Diese Adresse kannst du auf deinem Handy im selben WLAN öffnen und das Spiel direkt auf einem Touchscreen ausprobieren, inklusive sofortigem Neuladen, wenn du den Code änderst. Für ein Spiel, das ausschließlich für Fingertipps gemacht ist, ist das enorm praktisch.

Eine kleine Einschränkung solltest du kennen. Der Service Worker, also der Teil, der das Spiel offline verfügbar macht, wird im Code nur registriert, wenn die Seite über HTTPS läuft. Über die lokale Netzwerkadresse mit einfachem HTTP wird er also bewusst nicht aktiv. Das ist gut so, denn sonst würdest du beim Entwickeln ständig mit zwischengespeicherten alten Versionen kämpfen.

Wenn du eine fertige Produktionsversion bauen willst, nimmst du npm run build. Dieses Skript macht zwei Dinge hintereinander. Zuerst läuft der TypeScript-Compiler, allerdings nur als Prüfer. In der TypeScript-Konfiguration steht nämlich, dass er keine Dateien ausgeben soll. Er prüft also im strengen Modus alle Typen, und wenn etwas nicht passt, bricht der Build ab. Erst danach baut Vite das eigentliche Paket in den Ordner dist. Mit npm run preview kannst du dir diesen fertigen Build anschauen, ebenfalls im Netzwerk erreichbar.

Und dann gibt es noch npm run deploy. Das baut das Projekt und schiebt den Inhalt des dist Ordners mit dem Paket gh-pages auf einen eigenen Branch namens gh-pages, aus dem GitHub Pages die Seite ausliefert. Dabei wird eine Option gesetzt, die eine leere Datei namens nojekyll anlegt. Damit verarbeitet GitHub die Dateien nicht mit seinem Jekyll-Generator, sondern liefert sie unverändert aus.

Ein letzter Blick in die Vite-Konfiguration lohnt sich. Sie ist genau eine Zeile lang und setzt den Basispfad auf einen relativen Pfad, also Punkt Schrägstrich. Der Kommentar erklärt, warum: Derselbe Build soll sowohl auf GitHub Pages funktionieren, wo die App in einem Unterordner liegt, als auch später innerhalb der geplanten Capacitor-App, wo es überhaupt keinen Webserver-Pfad gibt. Mit relativen Pfaden findet die Seite ihre Skripte und Stile in beiden Umgebungen.

Zusammengefasst: klonen, npm install, npm run dev, Handy ins WLAN, fertig. Einfacher wird ein Web-Projekt kaum.

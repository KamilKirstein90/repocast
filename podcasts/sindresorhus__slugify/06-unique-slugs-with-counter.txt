We've covered every option of the main slugify function. Today we look at its sibling, slugify with counter, which solves the problem of duplicate slugs, and which hides more edge cases than you'd ever expect.

Here's the scenario. You're rendering a long document with many sections, and every section has a subsection called "Example". You want each heading to have an HTML ID so readers can link to it. But IDs on a page must be unique. If every one of those headings becomes just example, links will always jump to the first one. What you want is example, then example dash two, then example dash three, and so on.

That's exactly what this function does. When you call slugify with counter, you get back a new function. That function behaves like slugify, it takes the same string and options, but it remembers every slug it has produced. The first time you pass "foo bar", you get foo dash bar. The second time, you get foo dash bar dash two. And when you're done with one document and start the next, you call the reset method on it, and its memory is wiped. Because each call to slugify with counter creates a fresh, independent instance, two documents processed in parallel won't interfere with each other.

Let's look at how it's implemented. Inside the factory there are two pieces of state, created with closures. One is a map called occurrences, which counts how often each base slug has been seen. The other is a set called returned, which records every final result that has been handed out. Both use lowercased keys, so the uniqueness check is case insensitive, which matches how IDs are often compared in practice.

When you call the returned function, it first runs normal slugify. If the result is empty, it returns an empty string right away, without counting anything, so empty inputs never become dash two. Otherwise, it bumps the count for that slug in the occurrences map. If this is the second or later occurrence, it appends the count. There's also a bit of logic that strips any trailing number groups from the slug using the helper remove counter suffix, so it can take into account how often the plain version without numbers was used.

Now here's the really interesting part, which is explained in a comment in the code. The counter is keyed by the incoming slug. That means it can't see that a different input might already have produced the same result. Picture this: you pass foo, and get foo. You pass foo again and get foo dash two. Now you pass "foo 2", with a space and a two. Its plain slug is foo dash two, which has never been seen as an input, so the counter alone would happily return foo dash two again. That's a collision. To prevent that, after computing a candidate, the code checks the returned set. As long as the candidate has already been handed out, it bumps the number and tries again. In this example you'd get foo dash two dash two. The tests cover several orderings of this, including a chain where bar, bar two and bar three are taken, so the next plain bar has to skip ahead to bar dash four.

There's one more hidden gem: the remove counter suffix helper. Originally, stripping trailing number groups was done with a regular expression. But that pattern was unanchored, so on a pathological input like dash one repeated fifty thousand times, ending with a letter, the regex engine backtracked quadratically, and a single call took over thirty seconds. That's a denial of service waiting to happen if you slugify user content. The fix replaces the regex with a plain split on dashes and a loop that pops numeric parts off the end. It's linear and boring, which is exactly what you want. And there's a dedicated test that runs that malicious input and asserts it finishes in under five seconds, so the bug can't quietly come back.

The broader lesson here is that a tiny stateful wrapper can still have subtle invariants. The invariant this function promises is simple to state, never return the same slug twice per instance, and the code enforces it directly with a set rather than trusting the counting logic to be perfect.
